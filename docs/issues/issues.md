## 前提となるサービスの分担

| サービス | このサービスで担当すること |
| --- | --- |
| KAGO/App | 消費者のスキャン・かご・履歴・疑似購入。かごや履歴に基づく推薦候補の選定もAppで行う。推薦の選定・購入確定・実験群の割当など、利用者に改ざんされてはいけない処理は、ブラウザではなくAppのサーバー側処理（Next.jsのサーバー処理）で行う。 |
| KAGO/Ads | 店舗が広告を募集するポータル。メーカーが募集を探して広告を申請し、自社の成果を確認する。 |
| KAGO/Insight | 店舗がメーカー広告を承認・却下・停止する。店舗販促の条件設定、結果確認、施策更新を行う。 |
| KAGO/Signage | 店内画面へ承認済み広告を表示する。採用した場合はカメラで視認の可能性を推定する。 |
| KAGO/Core | 共通DB。テーブル、権限、整合性、DB関数・ビューを担当する。推薦エンジンや独立した業務APIは持たない。 |
| 共通 | 接続設定、開発環境、データ、通し確認、提出資料。 |

## この一覧の読み方

- 下の一覧からIssue名を選ぶと、このファイル内の詳細へ移動します。各Issueは同じ見出しの高さで並び、入れ子にしません。
- 「完成物」は、このIssueが終わったときに残るもの。「対象外」は別のIssueが担当する範囲です。
- 「先に必要なIssue」は接続・完了の前提です。画面やデータは仮の値で先行実装し、依存先の完成後に接続できます。
- 管理IDはこの資料内の参照用で、GitHubのIssue番号ではありません。担当者は各行・各詳細へ記入できます。
- 広い作業を分割したため、以前の37件から49件になっています。範囲を追えるよう、末尾に旧IDとの対応表を付けています。

## 優先度と実施区分

- P0：作業を止める障害などの至急対応。初期一覧には設定しません。
- P1：通常優先。P2：後回し可能。優先度は提案値です。
- 共通必須は完成を目指す基本経路。購入操作・データ代替・カメラ採用時・余力拡張は別の区分です。全49件の完成を一律に求める一覧ではありません。

| 実施区分 | 件数 | 扱い |
| --- | --- | --- |
| 共通必須 | 39 | 基本の改善ループを構成する作業 |
| 購入操作を実装 | 2 | 購入操作を通す場合のDB処理・App画面 |
| 余力拡張 | 6 | 基本経路ができた後に採用を判断 |
| カメラ採用時 | 1 | カメラを採用した場合のみ実装 |
| 購入をデータで代替 | 1 | 購入操作を省き、整合した架空注文で検証する経路 |

## 購入とカメラの選択

- 推奨の購入経路：[DB-07｜注文・明細・かご終了を一度に保存し、二重購入を防ぐDB処理を作る](#db-07)と[APP-09｜かごから疑似購入を完了し、注文を保存して次回来店の履歴へ反映する](#app-09)で、Appの疑似購入を完了させる。
- 代替の購入経路：[DATA-03｜架空の注文・明細を事前投入し、購入操作なしで履歴と購入集計を検証する](#data-03)で注文・明細を事前投入し、履歴・提案・購入集計を検証する。購入操作経路の完成を待たなくてよい。
- どちらか一方を選び、実際に操作して購入した記録と事前投入を区別する。どちらを選んだかはCOM-01の仕様書に記録する。両方を実装する必要はない。
- カメラは[SIG-04｜実機カメラで画面方向の顔向き・視線を推定し、採用する方式と判定条件を決める](#sig-04)で実機確認と採否を決め、採用時に[SIG-05｜カメラの推定視認人数・時間を再生中の広告に結び付けてDBへ保存する](#sig-05)を実装する。

## COM-01｜広告・提案・購買をつなぐ共通IDとデータ形式を仕様書にまとめる

| サービス | 担当者 | 優先度 | 実施区分 |
| --- | --- | --- | --- |
| 共通 | nine0511 | P1 | 共通必須 |

2026-10-24更新：GitHub [Issue #3](https://github.com/jphacks/hs_2604/issues/3)、作業フェーズ`hackday`（担当者指定）。[PR #52](https://github.com/jphacks/hs_2604/pull/52)で仕様書を更新。各担当の本人確認が終わるまでIssueは完了にしません。

**目的**

担当ごとに前提がずれないよう、今回の方針を実装前に揃える。

**完成物**

役割分担表、共通データ項目表、イベント・指標の定義、購入・カメラの実施方針をまとめた1つの仕様書。

**このIssueで行うこと**

- CoreはDBのみ、推薦の選定はAppという境界を文書化する。
- Adsの募集・メーカー申請、Insightの承認、Signageの表示・計測を整理する。
- 通常推薦・店舗販促・メーカー広告の種別、ID、時刻、表示・追加・購入の意味と数え方を決める。
- 集計の単位を、Appは利用者・来店、Signageは画面・時間帯とする。
- 購入経路（購入操作／購入データ代替）と、カメラ検証（SIG-04）の進め方を決めて記録する。

**このIssueに含めないこと**

- DBや画面の実装。DB設計はDB-01、各画面は各サービスのIssueで行う。

**何ができれば完了か**

- [ ] 5サービスの役割表と保存・参照・更新の対応表がある。
- [ ] 3種類の提案の区別と、表示・クリック・追加・購入を何をもって1件とするかが定義されている。
- [ ] 購入経路（APP-09またはDATA-03）の選択と、カメラ検証の方針が記録されている。
- [ ] 各画面担当が同じ架空例を追え、未決定事項と担当を記録している。

**確認方法**

1店舗・1メーカー・2利用者の例で、申請→承認→表示→反応→購入を机上確認する。

**先に必要なIssue**

なし。このIssueから開始できます。

**条件・補足**

このIssueの完成は、仕様書を作り、各担当が接続例と未決定事項を確認した状態。コードの実装完了を意味しない。

仕様書：[共通仕様書（v0.2 担当確認用）](../specs/common-spec.md)。2026-10-24に購入操作経路（DB-07＋APP-09）の選択、参照・集計・再送の条件、カメラ検証方針と机上確認を追記。未決定事項の確認・担当調整の窓口はnine0511です。各担当の本人確認（13章）と専門範囲の担当設定（12章）が残っています。

## 読み替え用の短い用語説明

| 用語 | 意味 |
| --- | --- |
| 来店・セッション | ある利用者の、ある店舗での1回の買い物。 |
| 通常推薦・店舗販促・メーカー広告 | 提案の3種類。通常推薦はかご・履歴に基づく提案、店舗販促は店舗が売りたい商品の提案、メーカー広告はメーカーが申請し、店舗が承認した広告（広告である旨と広告主を表示する）。 |
| 実表示 | 候補として選ばれただけでなく、実際に利用者の画面に表示されたこと。数える条件はCOM-01で定義する。 |
| 推定視認 | Signageのカメラで推定した、画面を見ていた可能性のある人数・時間。「見た」の断定ではない。 |
| 事前実装・Hack Day | 事前実装はハッカソン開始前に作成済みのコード。Hack Dayの成果と区別して記録する。 |
| 正本 | 件数や状態を判断するときに基準とする記録。購入数は注文・明細を正本とする。 |
| イベント | 表示・クリック・追加など、起きたことを時刻・ID付きで残す記録。 |
| 版 | その時点の広告・設定・ルールを識別する番号。更新前の結果と混ぜないために残す。 |
| DB関数 | DB内でまとめて保存・検証する処理。Appの推薦計算とは別。 |
| DBビュー | 保存されたデータを、利用目的に合う一覧・集計として参照する仕組み。 |
| 母数 | 割合を求めるときの分母。人数・来店数・表示数は異なる。 |
| 仮応答・モック | DB未完成でも画面を作るために使う、決めた形式の仮データ。 |
| サーバー側処理 | 利用者のブラウザではなく、Appのサーバー上で動く処理。利用者が値を書き換えられないため、推薦の選定・購入確定・実験割当に使う。 |
