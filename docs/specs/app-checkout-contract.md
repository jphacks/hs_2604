# APP-09: 疑似購入と注文の確認

作業フェーズ: hackday。対象: [Issue #25](https://github.com/jphacks/hs_2604/issues/25)。

かごの「疑似購入の確認へ」から `/App/checkout` を開く。購入確認と完了画面に実決済のないデモ操作であることを表示する。注文は共通仕様10章どおり `data_origin=operated`（画面からの実操作）で記録し、購入履歴にも「Appでの疑似購入」と表示する。実際のカード決済・POS連携は行わない。

`GET /api/checkout` は本人の選択中の来店を確認し、進行中なら既存 `app_get_cart` の最新価格・かご版・割引を使って明細を返す。小計・明細ごとの割引種別／割引額・割引合計・割引後合計を表示する。空のかご・取扱停止商品があるかごは確定不可とする。来店終了済みなら確定注文・注文明細・`order_discounts` から完了内容を返す。`visitId` による過去の本人の来店の読取も可能だが、別利用者には拒否する。

確定ボタンを押す前に、本人ID・来店ID・購入要求UUID・確認したかご版・割引後合計を利用者別sessionStorageへ保存する。`POST /api/checkout` は本人・customerロールを検証し、既存DB-07 `kago_checkout` を本人のセッションで呼ぶ。価格・版の確認、注文・明細・割引・来店終了の同時確定、同じ来店の一注文制約、同じ要求の再送はDB-07に委ねる。service roleや画面側の購入イベントは使用しない。

通信断・サーバー障害では元の要求を保持し、「同じ購入操作を再試行」か「購入結果を確認」を選べる。再試行でUUID・版・金額を変えない。価格変更・かご変更など、保存されなかったことが確定する応答では最新の明細を読み直し、新たな確定ボタンの操作を求める。古い金額で自動購入は行わない。連打中はボタンと送信をロックする。ストレージへ要求を保持できない場合は購入を送信しない。

購入確認ページは進行中の来店を必須とするAppの買い物Providerから分けている。来店が終了しても完了画面・未確認要求の復元を続けられる。完了後はURLに本人の確定来店IDを残し、再読込でも同じ注文を確認する。認証は購入APIで毎回行う。利用者・来店変更の通知では旧利用者の内容を隠し、遅い旧応答も無視する。未確認要求は利用者別のため、別利用者として送らない。同じ利用者が店舗を切り替えた後の再試行も、元の本人・来店・要求を維持する。

完了後に「次の買い物へ」でAppへ戻る。通常モードは店舗・来店選択、デモモードは既存の自動来店開始を使用する。次回来店の購入履歴に確定注文が入り、おすすめへの履歴利用がONならAPP-03の入力にも反映される。完了画面は購入時の単価・数量・割引を使い、後から商品価格が変わっても変化しない。

検証: `pnpm test:checkout`、`pnpm test:checkout:e2e`。ローカルのテスト用Auth/HTTPと正式なマイグレーション・RLSを適用したPGliteを使用する。割引なし・クーポン・セットの片方を削除・受け取り済みセール終了後・価格／かご変更・途中失敗・保存後の応答失敗・再送・本人以外を確認する。共有Supabase・実機カメラ・実決済の検証は含まない。
