# DEMO-01：利用者ごとのクーポン配布先を選ぶロジック

対象：[DEMO-01 / #112](https://github.com/jphacks/hs_2604/issues/112)（仕様）。実装は[DEMO-02 / #116](https://github.com/jphacks/hs_2604/issues/116)、データは[DEMO-05 / #113](https://github.com/jphacks/hs_2604/issues/113)、比較画面は[DEMO-07 / #118](https://github.com/jphacks/hs_2604/issues/118)。作業フェーズ：hackday。

既存仕様：[APP-13 セレンディピティ販促](app-serendipity-offers.md)、[APP-04 関連購買ルール](../../analysis/app04-association-rules/README.md)、[APP-03 履歴と利用設定](app-account-contract.md)。

## 目的と役割分担

利用者が商品をかごへ追加したとき、店舗が設定したゲリラクーポンの中から、その利用者に配る1枚を選ぶ。同じ商品を追加しても、購入履歴によって別の商品が選ばれる。

| 担当 | 決めること |
| --- | --- |
| 店舗（Insight／`store_offers`） | 商品ごとの値引き率・期間。全員に同じ値引き率 |
| KAGO/OS（App、本仕様） | 誰にどの商品のクーポンを配るか（最大1枚） |
| DB（APP-13の既存関数） | クーポンの有効性、割引額の計算・適用、受け取り。本仕様では変更しない |

機械学習モデルは使わず、同じ入力から必ず同じ結果になる説明可能な純粋関数とする。人ごとに値引き率を変えること、効果の統計的検証は対象外。

## スコア

```text
Score(u, t, p) = Association(t, p) × Novelty(u, p) × Deal(p)
```

- `u`：利用者。`t`：今回かごに追加したきっかけ商品。`p`：クーポン候補の商品。
- スコアが最も高い1件を選ぶ。候補がなければ配らない。

### きっかけ商品 t

その来店で最後にかごへ追加した商品（`cart_item_added`の最新で、まだかごにある商品）。数量の変更・削除は「追加」に含めない。クーポンを受け取って商品が追加された場合は、その商品が次のきっかけになる。1回の商品追加につき、配るクーポンは最大1枚。

### Association（関連の強さ）

APP-04のルール（`association-rules.json`、ルール版2）を使う。版2で生鮮商品を追加したが、デモで使う既存商品どうしのルールは版1と同じ。

| tからpへのルール | Association | 結果に残す出所 |
| --- | ---: | --- |
| 公開購買データ由来（`origin = analysis`） | `lift` | `analysis`、lift・confidence |
| 人手で補完したルール（`initialRules`、`origin = initial`） | `1.5`（既存`INITIAL_RELATION`と同じ） | `initial`、liftはなし |
| 店舗がtをきっかけ商品に指定したクーポン（ルールなし） | `1.2`（既存`STORE_TRIGGER`と同じ） | `store` |
| どれもない | 候補にしない | — |

- confidenceではなくliftを使う。目的は「次に買う商品を高確率で当てる」ことではなく、「その商品を買った人に特徴的な組み合わせ」からの出会い（セレンディピティ）のため。
- 同じ組み合わせに両方ある場合は公開データ（analysis）を優先する。
- 公開データはGroceries（arules、9,835件のレシート）。`pasta → domestic eggs`（スパゲッティ→新鮮たまご、lift 1.358）は公開データ由来。`スパゲッティ→生バジル`・`スパゲッティ→トマトパスタソース`は人手で補完したinitialルールで、公開データから算出した値ではない。画面・説明でも「すべて公開データから算出した」と誤認させない。

### Novelty（この人に今配る価値）

本人の購入履歴だけから決める。年齢・性別・家族構成などの属性は使わない（デモでU3を「子育て家庭想定」と紹介しても、計算には使わない）。

| 状態（上から順に判定） | Novelty | `noveltyReason` |
| --- | ---: | --- |
| 購入履歴の利用OFF | 1.0 | `history_disabled` |
| 購入履歴が空 | 1.0 | `history_empty` |
| 定期購入品 | 0.0（候補から除外） | `regular_purchase` |
| 購入経験あり、ただし定期購入品ではない | 0.6 | `purchased_before` |
| 対象商品は未購入、同カテゴリの商品は購入経験あり | 1.3 | `same_category` |
| 対象商品も同カテゴリ商品も購入経験なし | 1.0 | `never_purchased` |

Issue本文の案「過去1〜2回購入なら0.6」は、「購入経験あり、ただし定期購入品ではない → 0.6」に改めた。DATA-01では佐藤さんが卵を4回購入しており、回数だけで区切ると定義のない場合が生じるため。

カテゴリは商品マスタの`products.category`。

#### 定期購入の判定

APP-03の`buildPurchaseSummaries()`（来店開始時刻より前の注文、最新50件）の値を使う。

```text
定期購入品 ⇔ purchaseCount ≥ 3 かつ daysSinceLastPurchase ≤ averageIntervalDays × 1.5
```

`averageIntervalDays`が`null`（購入1回）の場合は定期購入としない。

この判定は`src/features/recommendations/purchase-cycle.ts`の`isRegularPurchase()`にあり、APP-05の補充推薦と「そろそろ買う頃です」カード（#152）も同じ定義を使う。定期購入品にはクーポンを配らず、代わりにカードで買い忘れを知らせる。

#### 履歴利用OFF

APP-03の`loadRecommendationInput()`の設計を維持する。`history.status === "disabled"`のときは購入履歴を読まず、選定にも渡さない。全候補のNoveltyを1.0とし、「過去の購入履歴から」「以前購入した」など履歴に基づく理由文を作らない。

### Deal（店舗の値引き率）

```text
Deal = 1 + discountPercent / 100        （25%OFF → 1.25、20%OFF → 1.20、15%OFF → 1.15）
```

割引額指定のクーポンは、DBが計算した1点あたりの割引額÷価格を値引き率とする。値引き率だけで決まらないよう、AssociationとNoveltyを補正する掛け算の1要素とする。

## 候補から除外する商品

| 条件 | 判定する層 |
| --- | --- |
| 無効・停止中、配布期間外、他店、店舗で販売停止中の商品 | DB（APP-13 `app_list_offers`。既存のまま） |
| この来店で受け取り済みのクーポン | DB（`app_list_offers`。既存のまま） |
| すでにかごにある商品 | 選定関数（`productInCart`） |
| この来店で「今回は見送る」を選んだクーポン | DBが本人の`offer_dismissed`記録から`dismissed`を返し、選定関数が除外 |
| 店舗が指定したきっかけ商品がかごにない | 選定関数（APP-13の既存条件） |
| tからの関連がない | 選定関数（Association） |
| 定期購入品 | 選定関数（Novelty） |
| この来店で受け取ったクーポンが3枚以上 | 選定関数（DBが受け取り枚数を返す） |

既存のAPP-13で保証済みの条件は二重に実装しない。

## 同点

スコアを小数第6位で丸めてから比べ（浮動小数点の誤差で順位が揺れないため）、同点は商品コードの昇順、さらに同じならクーポンIDの昇順。商品コードは環境（共有DB・検証DB）ごとにUUIDが異なっても変わらないため、商品IDではなく商品コードを使う。

## 結果

選定結果（`CouponScore`）には少なくとも次を含め、#118の比較画面でそのまま使えるようにする。

| 項目 | 内容 |
| --- | --- |
| `offerId`・`productId`・`productCode`・`productName` | 選ばれたクーポンと商品 |
| `trigger` | きっかけ商品t（コード・名前） |
| `score`、`breakdown.{association, novelty, deal}` | スコアと内訳 |
| `relation.{source, ruleId, lift, confidence}` | `analysis` / `initial` / `store`の区別。initial・storeのliftは`null` |
| `noveltyReason`・`discountPercent` | Noveltyの区分と値引き率 |
| `reason` | 理由文 |

候補全体（順位順）と除外した商品・理由も返す（比較画面・確認用）。

## 理由文

実際に計算に使った情報だけから作る。

| 部分 | 文 |
| --- | --- |
| 関連（analysis） | 公開購買データ（Groceries）では{t}と一緒に買われやすい組み合わせです。 |
| 関連（initial） | {ルールの理由}（KAGOが登録した組み合わせ）。 |
| 関連（store） | 店舗が{t}と一緒に案内しているクーポンです。 |
| 新しさ（`purchased_before`） | 以前購入したことがあり、定期的には購入していない商品です。 |
| 新しさ（`same_category`） | 購入したことのある売場の、まだ購入したことのない商品です。 |
| 新しさ（`never_purchased`） | まだ購入したことのない商品です。 |
| 新しさ（履歴OFF・空） | なし（履歴に触れない） |
| 値引き | {25%OFF}でお得なため選ばれました。 |
| 定期購入品を除外した場合 | 定期的に購入している商品は候補から外しています。 |

例：

- 田中さん（履歴OFF）：「スパゲッティの仕上げに合います（KAGOが登録した組み合わせ）。25%OFFでお得なため選ばれました。」
- 佐藤さん：「公開購買データ（Groceries）ではスパゲッティと一緒に買われやすい組み合わせです。以前購入したことがあり、定期的には購入していない商品です。20%OFFでお得なため選ばれました。定期的に購入している商品は候補から外しています。」
- 鈴木さん：「スパゲッティと一緒に使えます（KAGOが登録した組み合わせ）。まだ購入したことのない商品です。15%OFFでお得なため選ばれました。」

## デモ3人の期待結果

前提：DEMO-05（#113、PR #126）のデータ。候補はゲリラクーポン3件（きっかけ商品の指定なし）、全員がスパゲッティ 500g（`2900000000100`）をかごへ追加。基準時刻は来店開始2026-10-25 12:00（日本時間）。

| 候補 | 値引き率 | Deal | Association |
| --- | ---: | ---: | --- |
| 生バジル（`2900000000179`、青果） | 25% | 1.25 | 1.5（initial `init-pasta-basil`） |
| 新鮮たまご 10個（`2900000000063`、卵） | 20% | 1.20 | 1.358（analysis `grc-2900000000100-2900000000063`、pasta→domestic eggs） |
| トマトパスタソース（`2900000000162`、調味料） | 15% | 1.15 | 1.5（initial `init-pasta-sauce`） |

各利用者の履歴（候補商品について）：

- U1 佐藤：生バジル・トマトパスタソースを10/10・10/17・10/24に購入（3回、平均7日、最後から1日 ≤ 10.5日 → 定期購入品）。新鮮たまごはDATA-01で8/28〜10/3に4回（平均12日、最後から約22日 > 18日 → 定期購入品ではない）。
- U2 田中：履歴利用OFF。
- U3 鈴木：生バジル・新鮮たまごを10/1に1回ずつ購入。トマトパスタソースと同じ調味料は購入なし。牛乳・パンは週1回（候補ではない）。

| 利用者 | 履歴 | 生バジル | 新鮮たまご | トマトパスタソース | 選択 |
| --- | --- | ---: | ---: | ---: | --- |
| U2 田中 | OFF | 1.5×1.0×1.25＝**1.875** | 1.358×1.0×1.20＝1.6296 | 1.5×1.0×1.15＝1.725 | **生バジル** |
| U1 佐藤 | ON、バジル・ソースが定期購入品 | 除外 | 1.358×0.6×1.20＝**0.97776** | 除外 | **新鮮たまご** |
| U3 鈴木 | ON、バジル・卵を購入経験あり | 1.5×0.6×1.25＝1.125 | 1.358×0.6×1.20＝0.97776 | 1.5×1.0×1.15＝**1.725** | **トマトパスタソース** |

佐藤さんは総合スコアの高さではなく、定期的に買う商品へ「どうせ買う商品の値引き」を配らない点が要点。liftの実値はコード内のルールファイルを正とする。

### 期待結果が変わる条件（デモ時の注意）

- 佐藤さんの生バジル・ソースは、3回目の購入（10/24 12:00）より後に来店を開始し、かつ最後の購入から10.5日以内（11/3 24:00まで）のときだけ定期購入品になる。10/24 12:00より前に開始した来店では購入2回のため定期購入品にならず、生バジル（1.5×0.6×1.25＝1.125）が選ばれる。
- 佐藤さんの新鮮たまごは、最後の購入（10/3）から18日以内に開始した来店（10/21より前）では定期購入品になり、配らない。
- 値引き率をInsightで変えると結果が変わる（例：田中さんでソースを30%にすると1.5×1.30＝1.95で生バジルを上回る）。

### デモ用の固定（#186）

デモでは、スパゲッティ（`2900000000100`）を読み取ると、上の表やスコアにかかわらず**誰でも**トマトパスタソース（`2900000000162`）のクーポンを出す（`targeting.ts`の`DEMO_PINNED_COUPONS`）。上の表はスコアだけで選んだ場合の結果として残す。

- ソースのクーポンがDBで配布中で、ソースがかごにない・今回見送っていない・受け取り上限（3件）に達していないときだけ出す。出せないときは通常のスコアで選ぶ。
- 理由文は「スパゲッティと一緒に使えるクーポンです。15%OFFでお得です。」（履歴は使わない）。
- 固定をやめるときは`DEMO_PINNED_COUPONS`を空にする。

## 実装上の約束（#116）

- 選定は純粋関数（DBアクセス・現在時刻・乱数を使わない）。履歴・設定はAPP-03の`loadRecommendationInput()`で毎回取得する。
- 割引額の計算・適用・受け取りはAPP-13のDB関数のまま。Appはどのクーポンを出すかだけを決める。
- セット割・タイムセールの表示はAPP-13のまま変更しない。
- APP-13で「店舗がきっかけ商品を指定したクーポンを優先」としていた順位は、本仕様のスコアに置き換える（指定はAssociationの出所`store`として残る）。

## 生鮮商品のクーポン（#158）

`kago-core/supabase/seed/app_fresh_coupons.sql`で、#144の生鮮のうち3品に店舗の値引きを設定する（豚こま切れ20%・鶏もも肉15%・ロースハム25%、期間はDEMO-05と同じ）。誰に配るかは本仕様のスコアのまま。

- スパゲッティから関連ルール（版2）がある生鮮（トマト・にんじん・合いびき肉など）には設定しない。上記3品はスパゲッティからのルールがないため、3人の期待結果は変わらない。
- 例（履歴OFF）：食パン→ロースハム、合いびき肉→鶏もも肉。牛こまは田中さん（OFF）には生バジル、佐藤さんには生バジルが定期購入品で外れるため豚こま切れ。
- 野菜は、スパゲッティからルールがある品目（other vegetables・root vegetables）しかないため、今回は設定しない。
