# APP-08: かごに合わせた推薦の更新

作業フェーズ: hackday。対象: [Issue #24](https://github.com/jphacks/hs_2604/issues/24)。

来店のかごをDBから読み込んだ後、および追加・削除・数量変更・販促適用によって保存済みのかご版が変わった後に、App内の既存 `GET /api/recommendations` を呼ぶ。選定計算と記録はAPP-05を使用する。Coreの別HTTP APIは追加しない。

選定要求だけを250ms待ち合わせる。待ち合わせ中にかご版が再び変わった場合は最後の版にまとめる。かご操作はAPP-02でその都度保存し、イベントと版の加算も各操作で行う。同じ来店・かご版の再描画やかごの読み直しでは選定をやり直さない。

来店・かご版が変わった描画から、古いカードと詳細を取り下げ、「かごに合わせておすすめを更新しています」と表示する。古い提案をクリック・追加したり、更新待ちの古いカードを実表示として記録したりしない。新しい選定は先頭のスライドから表示し、利用者が選んだ自動切替の停止状態は維持する。正常な空候補と通信失敗は別に表示する。

応答は、来店ID・かご版・現在の要求順がすべて一致した場合にのみ採用する。前の要求をAbortControllerで中止し、要求番号でも確認するため、通信層が中止に従わない場合も古い成功・失敗の応答を反映しない。来店・利用者切替で古い処理を停止する。

`input_changed` または応答のかご版不一致は、別タブ等によってDB側が進んだ可能性があるため、かごを読み直して選定を一度だけ自動再試行する。再び一致しない場合はエラーと再試行ボタンを表示し、無限再試行・永久に消えない読み込み表示を避ける。かごの読み直しで新しい版が届けば、その版で通常どおり再開する。来店不一致・認証切れではセッションも確認する。

サーバーでは候補なしの場合も、応答前にかご版を再確認する。枠がある場合は選定枠の取得後に確認する。画面の再描画で表示数を増やさない仕組みは[APP-07のイベント接続契約](app-events-contract.md)を引き続き使用する。

検証: `pnpm test:refresh`、`pnpm test:refresh:e2e`、既存の選定・かご・イベントのテスト。ブラウザ検証は正式なSQL・RLSを適用した使い捨てPGliteとローカルAuth/HTTPアダプターを使用する。共有Supabase・実機カメラの動作確認は含まない。
