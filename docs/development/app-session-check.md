# APP-01：残る実接続の確認

対象：[APP-01 / #17](https://github.com/jphacks/hs_2604/issues/17)。2026-10-24・hackday。DB-06は[PR #67](https://github.com/jphacks/hs_2604/pull/67)でmainへマージ済みです。正式権限でのローカル統合検証に切り替えています。共有Supabaseの接続設定・実行結果は未確認です。

画面・接続処理・来店開始関数は[接続仕様](../specs/app-session-contract.md)に記載しています。DB-05のテーブル追加だけでは、DB-06のアクセス許可は有効になりません。検証処理は管理キー、DBへのGRANT追加、架空データへの自動切替を使いません。

## 準備

1. DB担当が開発用SupabaseへCOM-02〜DB-05、APP-01のmigration、DB-06の権限・RLSを適用したことを確認します。適用順は[共通DBガイド](database.md)を参照してください。チェッカー自身はmigrationを適用しません。
2. 共通基盤と同じ`customer`役割の検証専用アカウントを2件用意します。実利用者のアカウントは使いません。店舗・商品はDATA-01などで用意してください。
3. 両アカウントの検証店舗の進行中の来店に、それぞれ1件以上の異なるかご商品を用意します。空のかごだけで復元を確認したことにしません。商品追加のUI実装はAPP-02なので、未実装の場合は管理者が専用の架空データを投入します。
4. `kago-os/kago-app/.env.shopping-check.example`を同じ場所の`.env.shopping-check.local`へコピーし、接続URL・publishable key・店舗UUID・2アカウントのメール／パスワードを設定します。今回の作業場には上書きせず入力用ひな形を作成済みです。ファイルはGit管理外です。チャット・Issue・PRへ認証情報を貼らず、接続先の確認時はファイルの場所だけを共有してください。

## 実行

Node.js 22、pnpm 11.19.0を使い、`kago-os/kago-app/`から実行します。

```sh
pnpm check:shopping
```

既定の`KAGO_CHECK_ALLOW_VISIT_WRITE=0`は読取専用です。ログイン／ログアウトは専用クライアントのメモリ内セッションで行い、ブラウザで利用中のセッションには接続しません。件数・確認の成否だけを出力し、メール・パスワード・トークン・利用者UUIDを出力しません。失敗時は終了コード1で停止し、未確認項目を成功扱いにしません。

| 確認 | 成功条件 |
| --- | --- |
| 本人 | 異なる2利用者が`customer`としてAuthで検証される |
| 店舗・来店 | 両利用者が同じ検証店舗と本人の進行中の来店を参照できる |
| かご復元 | 両方のかごに商品があり、再取得しても同じ来店・商品・数量・価格になる。行の順序だけの違いは無視 |
| 他人参照の拒否 | 他人の来店IDを指定してもかごを返さず、本人のSupabaseクライアントで直接`visits`・`cart_items`を要求しても他人の行を取得できない |
| ログアウト後 | 片方のセッションを終了した後は本人のかごを取得できない |

`database_not_ready`ならmigrationとテーブル権限を確認します。`forbidden`ならAuthの`app_metadata.kago.roles`とRLSを確認します。接続エラーと権限不足を、別の架空利用者や管理キーへの切替で回避しません。

## 書込みを含む来店確認

**専用の検証アカウントだけ**で、環境ファイルの`KAGO_CHECK_ALLOW_VISIT_WRITE=1`を明示した場合、追加で来店開始／再開・明示的新規来店・同じ要求の再送を確認します。最後には指定した両アカウントの進行中の来店が終了し、新しい空のかごへ移ります。旧来店のかごは過去の記録として残り、削除しません。

読取専用モードや、かごに商品がない状態の実行を、書込み確認まで完了した結果として記録しません。実行するたびに同じ結果を得るには、両利用者のかごの検証データを改めて用意してください。

## ブラウザで確認する残件

チェッカーはAppと同じサービス処理をSupabaseへ接続して検証します。Cookieを含む実ブラウザの確認は別に行います。

1. 同じSupabaseに接続するAppを開き、2利用者でログイン→店舗選択→来店開始／再開→かご表示を確認。
2. 再読込で同じ来店・かごを復元し、アカウント切替・別タブログアウト後に前のかごが残らないことを確認。
3. 明示的新規来店が空の別かごになり、再読込では新規来店が増えないことを確認。
4. 管理者による検証セッションの失効で再ログイン案内を確認。通常のアクセストークン期限は自動更新される場合があるため、単なる待機だけで失効確認済みとしない。
5. 接続失敗時の案内・再試行を確認。

実行日・接続先が開発用であること・読取専用／書込みの別・成功した項目・残る項目をIssue #17へ記録します。秘密情報は記載しません。実DBとブラウザの両方を確認するまで、APP-01の完成条件を完了にしません。

## ローカルの再現テスト

```sh
pnpm test:shopping:database
pnpm test:shopping:check
pnpm test:shopping:e2e
```

DB統合試験はDB-06までの実SQLをPGliteへ適用し、正式なポリシー・関数・テーブル権限だけで実行します。追加の許可は付けません。JWTの検証済みclaimsはローカルで模擬しています。チェッカー自身の試験・ブラウザE2Eは検証用HTTP応答を使います。いずれも、共有Supabaseで検証した結果ではありません。

DB-06マージ前には計51テスト・ブラウザ16ケースが成功しました。マージ後は仮の許可を削除し、2つのAppクライアントで本人の来店・かご復元、他人の来店指定と直接DB参照の拒否、ログアウト後の拒否を正式ポリシーで再検証しました。検証用HTTPアダプターはリクエストごとに利用者ロールを固定し、PGliteの1接続上で並列要求の権限が混ざらないよう直列化しています。

実接続コマンドも再実行しましたが、環境ファイルがなく停止しました。その後、入力用ひな形を新規作成し、実値未設定（最初の不足項目は`KAGO_CHECK_STORE_ID`）で終了コード1になることを確認しました。接続情報・検証アカウントは未入手のため、共有Supabaseへの実接続と実際の失効操作は未実施です。

DB-06マージ後の再実行では、統合11件・接続11件・チェッカー4件・共通基盤26件の計52件と、ブラウザ16ケースが成功しました。正式なDB-02〜DB-06付属検証SQLもすべて成功し、型検査・lintも通っています。
