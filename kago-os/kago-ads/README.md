# kago-ads

KAGO/OS のうち **KAGO/Ads**（店舗の広告募集・メーカーの広告申請）と **KAGO/Signage**（店内サイネージの全画面表示・再生記録）の画面です。**Signage もこのアプリにあります**（`/signage`。2026-10-24 決定。開発ガイドにある `kago-signage/` は作りません）。Ads のデータ項目・状態・素材の仕様は [docs/specs/ads-spec.md](../../docs/specs/ads-spec.md) にまとめています。

**ADS-01の募集閲覧、ADS-02の募集作成・公開・終了、Signage（SIG-01〜03）の端末ログイン・配信内容・再生記録はSupabaseへ接続します。** 申請保存は仮実装のため、接続済みの範囲を分けて扱います。

## ADS-01：共通認証と募集ポータルのDB接続

既定は `supabase` モードです。メーカーの実ログイン、`maker_members` の所属確認、店舗・募集の一覧／詳細、公開される成果の範囲、稼働中端末の設置場所、自社の申請済みIDを読取専用で取得します。DBにない店舗紹介・住所を仮の値で補いません。

```bash
cp .env.example .env.local
# .env.localをローカルで編集し、同じSupabaseプロジェクトのURLとpublishable keyを設定
pnpm dev
```

- `NEXT_PUBLIC_ADS_DATA_SOURCE=supabase`（未指定も同じ）を使用。URL・公開キーが不足／不正なら設定エラーを表示し、仮データには戻りません。変更後は再起動・再ビルドが必要です。
- アカウントは管理者が作成し、`app_metadata.kago.roles` に `maker_staff`、`maker_members` に本人Auth UUIDとメーカーUUIDを設定します。[共通認証ガイド](../../docs/development/backend.md)を参照してください。所属なし・別役割は拒否します。
- `/ads/portal` を開いてログインします。未ログイン時に募集を一般公開しません（DB-06はanonへ読取を許可しない）。`?as=...` やlocalStorageの仮セッションは実認証に使いません。
- DB-02・DB-04・DB-05・DB-06と前提migrationを適用した環境を使います。適用履歴を確認し、共有環境へ重複適用しないでください。ブラウザは公開キーと本人セッションで接続し、管理キーを使いません。
- 複数所属がある場合、募集一覧は各店舗の公開済み募集、自社申請は本人が所属するメーカーのものを取得します。RLSでさらに制限されます。
- ADS-03の素材登録・申請保存、審査の確認用画面は実接続モードでは準備中の案内を出します。実ログインを仮データの書込みへ流さないためです。申請への入口は募集詳細に残しますが、保存はまだできません。

### 従来の仮データでの確認

`.env.local` に `NEXT_PUBLIC_ADS_DATA_SOURCE=mock` を明示して再起動・再ビルドしてください。以下にある役割切替・初期化・Adsの保存はこのモードに限ります。Signage もこのモードでは仮データ版（端末 ID だけで入れる）になります。

### 実Supabaseでの読取確認

`.env.local` にサーバー用の `KAGO_ADS_CHECK_EMAIL` と `KAGO_ADS_CHECK_PASSWORD` を追加し、`pnpm check:portal` を実行します。メーカーの認証・所属、店舗と募集の読取、ログアウト後の拒否を確認します。業務データは変更せず、認証情報や行の内容は出力しません。値をGit・Issue・PR・チャットに貼らないでください。

2店舗以上の募集・終了募集・募集0件の店舗はDATA-01等で用意する必要があります。このチェックの成功だけで、他社・下書きの拒否や別端末での実演まで確認済みにはしません。

### ローカル検証

```bash
pnpm test
pnpm lint
pnpm exec next typegen
pnpm exec tsc --noEmit
pnpm build --webpack
pnpm test:portal:e2e
```

- `pnpm test` は正式な全migrationを破棄可能なPGliteへ適用し、メーカー2社・2店舗、下書き・終了募集、所属なし・別役割・ログアウト・失効、自社申請の範囲を確認します。テスト用の追加GRANT・ポリシーは使いません。
- `pnpm test:portal:e2e` は架空の公開接続値で本番ビルドを作り、ポート3189で一時起動します。既存のChrome（Linuxでは `/usr/bin/google-chrome`、別パスは `CHROME_PATH`）で実操作します。認証とHTTP転送は検証用、DB行とRLSはPGliteの正式SQLです。実SupabaseのAuth署名・PostgREST・Storageの確認ではありません。
- このコマンドは `.next` を検証用ビルドに更新します。確認後に配布する場合は実環境の設定で再ビルドしてください。スクリーンショットは `docs/images/ads01-login.png`・`ads01-portal.png`・`ads02-edit.png`・`ads02-calls.png` に保存します。
- 共有Supabaseへの適用、実アカウントと実端末での通し確認は別途必要です。

## ADS-02：店舗の募集作成・公開・終了

1. ログイン画面で「店舗担当者」を選び、`store_staff` のアカウントでログインします。本人Auth UUIDと店舗UUIDの対応が `store_members` に必要です。所属なし・別役割は拒否します。
2. `/ads/store/calls` で自店の募集を確認します。複数店舗に所属する場合はヘッダーの「操作する店舗」で選択します。選択変更時は前の店舗のフォーム・読取結果を残しません。
3. 募集名・カテゴリ・掲載期間・掲載先・案内文・成果の公開範囲を入力し、「下書き保存」または「保存して公開」を選びます。保存先は本人の所属を検証した選択店舗です。初回はdraftで保存し、公開時にopenへ変更します。
4. 公開後は期間と掲載先を固定します。募集名・カテゴリ・案内文・公開範囲は編集できます。終了後は編集・再公開できません。期間は最終日の翌日0時を含まない境界で保存します。
5. 募集の公開は広告の承認ではなく、終了しても既存の広告配信を停止する操作にはなりません。審査・配信の停止はInsight／DB-08で行います。

更新時はフォームが読んだ `updated_at` と現在の状態を照合します。別の担当者が先に変更・終了した場合は上書きを拒否し、再読み込みを案内します。保存成功後に公開処理が失敗した場合、同じフォームで再試行しても既に保存した募集IDを再利用します。

成果の公開範囲は `disclosure_scope` に保存します。0項目は「成果を公開しない」です。メーカー向けのDB集計もDB-09の公開制御に従い、画面で隠すだけの認可にはしません。ADS-04の画面接続は別作業です。

### 実Supabaseで店舗の接続を確認する

`.env.local` の公開接続値に加え、以下をローカルで設定してください。値はGit・Issue・PR・チャットへ貼らないでください。

```dotenv
KAGO_ADS_STORE_CHECK_EMAIL=検証用店舗アカウントのメール
KAGO_ADS_STORE_CHECK_PASSWORD=検証用店舗アカウントのパスワード
# 複数所属から確認対象を選ぶ場合だけ指定。未指定なら所属店舗の1つを使用
KAGO_ADS_CHECK_STORE_ID=所属している検証店舗のUUID
```

`pnpm check:store-calls` は店舗の認証・所属・自店募集／カテゴリの読取・ログアウト後の拒否を確認します。業務データの書込みは行わず、接続値・認証情報・行の内容も出力しません。

書込みと画面の実確認は、2店舗分の店舗担当者とメーカーの検証用アカウントで行います。

- 店舗Aで検証用の募集を下書き保存し、メーカーから見えないことを確認する。
- 店舗Aで編集・公開し、別ブラウザのメーカーが同じ募集と公開範囲を確認する。
- 店舗Bで同じ募集の編集URLを開き、読取・変更が拒否されることを確認する。
- 店舗Aで募集を終了し、メーカーの画面から新しい申請へ進めなくなることを確認する。
- 募集の公開だけで広告の配信対象が作成されていないことを確認する。

この研究室PCでは接続用 `.env.local` が未設定のため、上記の共有Supabaseでの確認は未実施です。ローカルでは正式migration・RLSを使ったテスト80件と、Chromeによるブラウザ操作28項目で確認します。Auth応答とHTTP転送は模擬であり、実Supabaseの署名・PostgRESTを検証した意味ではありません。

## 仮データモードの起動・確認

Node.js 22・pnpm 11.19.0 を使います（`kago-os/` 全体が pnpm のワークスペース）。

```bash
cd kago-os
pnpm install --frozen-lockfile
cd kago-ads
pnpm dev        # http://localhost:3000/ads
pnpm test       # 判定ルールとデータ層のテスト（vitest）
pnpm lint
pnpm build
```

右上の「ログイン（デモ）」で役割を切り替えます。URL に `?as=store_staff:S1` や `?as=maker_staff:M1` を付けても切り替えられます。「仮データを初期化」で最初の状態に戻ります。仮データは共通仕様書 11 章の架空例（広島デモ店・瀬戸内トマト食品・トマトパスタソース）で、日付は今日を基準に作ります。

| 役割（共通の認証の roles） | できること |
| --- | --- |
| `store_staff`（広島デモ店／駅前店） | ADS-02：自店の募集の作成・編集・公開・終了、成果の公開範囲の設定。審査（確認用） |
| `maker_staff`（瀬戸内トマト食品／確認用メーカー） | ADS-01：募集を探す。ADS-03：広告素材と版の登録・申請・再申請・結果の確認 |

`/ads/dev/review` の審査画面は、INS-01（KAGO/Insight）と DB-08 ができるまでの確認用です。Insight ができたら削除します。

| URL | 内容 |
| --- | --- |
| URL | DB 版（既定） | 仮データ版（`mock`） |
| --- | --- | --- |
| `/signage` | 端末の画面へのリンクだけ | 端末を選ぶ入口 |
| `/signage/play` | 端末のアカウントでログインして全画面表示。端末・店舗はアカウントから決まり、URL では選ばない | `?device=D1` のように端末 ID を付けて開く |

どちらも `?debug=1` を付けると、通信・表示中・キャッシュ・未送信の記録・接続先の状態と、確認用のボタン（「通信を切る」、DB 版は「端末からログアウト」）を出します。

会場の端末では Chrome のキオスクモードで開きます（クリックでも全画面になります）。DB 版は最初の1回だけ端末のアカウントでログインし、ログイン情報はその端末の Chrome に残ります。

```bash
google-chrome --kiosk --autoplay-policy=no-user-gesture-required "https://<デプロイ先>/signage/play"
```

### DB 版（SIG-01〜03 の Supabase 接続）

- 端末のアカウントは管理者が作ります。`app_metadata.kago` に `roles: ["signage"]`・`device_id`・`store_id` を入れ、`signage_devices.auth_user_id` を本人に合わせます（DATA-01 の DV1〜DV3 がこの形。[共通認証ガイド](../../docs/development/backend.md)）。別の役割のアカウントでは入れず、ログイン情報も残しません
- 読むもの（`src/lib/backend/signage.ts`）：自端末・自店、配信中の配信対象（`ad_placements`）と販促の版、その素材の版・商品・店舗別価格・メーカー名。端末には停止中のものが見えない（DB-06）
- 書くもの：自端末の再生記録（`signage_plays`）だけ。まとめて送って通らなかったときは1件ずつ送り直し、受け付けられない記録（中身の違う再送・配信期間の外など）だけを捨てる。捨てた件数は状態表示に出す
- 停止と更新の見分け：再生中のものが一覧から消えたとき、同じ申請・販促（`group_key`）の新しい版がなければ停止とみなしてすぐ切り替え、新しい版があれば更新として下の「切り替え」の決まりで待つ
- 素材：非公開 Storage（`ad-images`）の画像をその都度署名付き URL で読み（URL は保存しない）、読めた画像をブラウザの Cache に保存する（`src/features/signage/media.ts`）。版ごとにパスが変わるので、保存した中身は古くならない
- 「端末からログアウト」で、保存した画像と配信内容も消す
- デモ用の時刻は DB にないので、DB 版は実時刻で判定する（COM-01 案 G）

共有 Supabase での確認手順は、端末アカウントで `kago-app` の `pnpm check:backend`（`KAGO_CHECK_ROLE=signage`）を通してから、本番ビルド（`pnpm build` → `pnpm start`。Service Worker は本番ビルドだけで動く）で `/signage/play?debug=1` を開きます。端末のパスワードは Git・Issue・PR・チャットに貼らないでください。

### 共有Supabaseでの実接続確認（2026-10-24）

研究室PC上の本番ビルドをChromeで操作し、公開キーと端末・店舗・メーカー本人のセッションで15項目を確認しました。Auth・PostgREST・Storageは実環境です。

- DV1でログインし、承認済み画像・広告表記・店舗価格298円・全画面表示を確認。
- ブラウザから生じた終了済みの再生記録を共有DBで確認。同じIDを再送しても1件のままで、端末から個人の来店・注文を読めないことを確認。
- 再読込後もログインを維持。ブラウザの通信を実際に遮断しても画像表示を継続し、切断中の再読込でもキャッシュから表示。
- 切断中に**端末内キャッシュの期限だけを過去に変更**し、広告を止めて案内へ切替。サーバーの配信期間や時計は変更していない。
- 再接続後は、終了済みの未送信記録がすべてDBへ届き、最新の配信取得と表示が再開。デバッグの未送信件数には再生中の未完了1件も含まれるため、件数0ではなく終了済み記録の到達を照合した。
- ログアウト後は表示・配信内容・画像キャッシュを消去。
- 2号店に検証専用の募集・素材・申請を作り、T2の正式な承認関数でSignageだけ承認。DV3で278円の店舗別価格を表示し、正式な停止関数で停止した後の切替と停止記録を確認（停止操作から表示・記録確認まで約10.1秒）。
- 専用広告は停止、専用募集は終了済み。既存DATA-01の承認済み広告は前後で同一、ADS-03の検証申請は操作していない。検証用の素材・画像・審査履歴・再生記録は残る。
- 認証情報・署名付きURLは公開記録へ残していない。会場の物理ディスプレイ・会場回線での確認はTEST-02（#50）で別途行う。

![共有Supabaseの承認済み広告と店舗価格](../../docs/images/signage-live-display.png)

決まり（COM-01 案 C・E・F・G、共通仕様書 8.3・9.3）：

- 出すもの：自店で承認済み（`active`・期間内・掲載先に Signage）のメーカー広告と、時間帯・期間内の店舗販促。広告（承認順）と販促（優先度順）を交互に流す。出せるものがなければ案内（`mode = fallback`）
- 画像は1枠10秒、動画は最後まで。5秒ごとに取り直し、内容が変わったら画像は表示3秒以上で、動画は終わってから切り替える（新しく入ったものを先に出す）。停止・期間や時間帯の終わりはすぐ切り替える
- 取得した内容の有効期限は10分。通信が切れても期限まで表示を続け、過ぎたら案内にする。素材は先に読み込み、`/signage/` の範囲の Service Worker（`public/signage/sw.js`、本番ビルドのみ）が保存する
- 再生記録は再生の開始と終了ごとに端末で作り（id は端末が採番）、端末に貯めて5秒ごとに送る。同じ id は1件にまとめるので、再送しても増えない。「再生1回」は「終わっていて3秒以上・案内ではない・動画は最後まで再生」（`src/lib/signage/plays.ts` の `isCountedPlay`。DB-09 に渡す）
- 端末は利用者・来店・かご・注文を読まない。記録にも `user_id`・`visit_id` を持たない

仮データ版では Ads と Signage が同じブラウザの localStorage を共有します。確認画面（別のタブ）で販促を止めると、端末の画面は次の取得（5秒以内）で切り替わります。

## 構成

kago-app と同じ形にしています。

| 場所 | 内容 |
| --- | --- |
| `src/app/` | ページとレイアウト。`/ads/store/calls`（ADS-02）、`/ads/portal`（ADS-01）、`/ads/maker/creatives`・`/ads/maker/applications`（ADS-03）、`/ads/dev/review`、`/signage`・`/signage/play`・`/signage/dev`（SIG-01〜03） |
| `src/features/` | 機能ごとの画面。`ad-calls`（ADS-02）・`portal`（ADS-01）・`creatives`・`applications`（ADS-03）・`dev-review`・`shell`（ヘッダー・入口）・`signage`（端末の画面と再生の仕組み `engine.ts`・確認画面） |
| `src/components/` | 機能をまたいで使う部品。`ad-media.tsx` は素材の表示と「広告｜提供」・価格の重ね表示、店舗販促の表示（`PromoMedia`）。ADS-03 のプレビューと Signage の全画面表示で同じものを使う |
| `src/lib/domain/` | 型（共通仕様書の列名のまま）、判定ルール、素材の仕様 |
| `src/lib/signage/` | Signage の配信内容の組み立て（`feed.ts`）、切り替えの判定（`player.ts`）、再生記録の数え方（`plays.ts`）。画面から切り離した関数でテストする |
| `src/lib/data/` | データの窓口（`repository.ts`）と仮データ版（`mock-repository.ts`）。画面はここだけを通して読み書きする |
| `src/data/demo/` | 仮データ（`seed.ts`）、広告素材・商品の対応表（`ad-assets.csv`・`products.csv`） |
| `public/ad-assets/` | ADS-05 のデモ広告素材（画像・動画） |
| `scripts/ad-assets/` | 素材と対応表を作り直すスクリプト（ADS-05） |

Next.js の約束：描画中に現在時刻を読まず、`today()` は読み込み後やイベントの中で呼ぶ。URL のパラメータを読む画面は `<Suspense>` で包む。
